# Формат входного Excel

Имя файла должно содержать `Меню_Продажи` без учёта регистра, расширение — `.xlsx`. Подходят, например, `Меню_Продажи.xlsx` и `Отчёт_Меню_Продажи_октябрь.xlsx`.

## СПР

| Столбец | Содержание |
|---|---|
| `Позиция` | Исходное название нового/сезонного блюда |
| `группа` | Группа меню |
| `Новое` | 1 — новое; 0 — сезонное |
| `старт` | Общая дата запуска блюда |
| `Позиция с корректировкой` | Необязательное каноническое название |
| `Мозг` | Необязательный псевдоним названия |
| `Код` | Обязательный код блюда для списка запусков |

Справочник содержит оцениваемые новинки и сезонные блюда. Обычное меню берётся из «Потока продаж». Искусственный пример содержит коды СПР и отдельный список запусков.

## Рестораны_Блюдо

Обязательный лист для новых загрузок Excel. Одна строка — один запуск блюда в ресторане.

| Столбец | Содержание |
|---|---|
| `Код` | Код блюда, сопоставляемый с `Код` в СПР |
| `Ресторан` | Название ресторана из продаж и чеков |
| `Позиция` | Необязательное название для человека; не участвует в сопоставлении |

Каждый код СПР должен присутствовать хотя бы в одной заполненной паре, включая сезонные блюда, будущие запуски и блюда без продаж. Иначе загрузка отклоняется с перечнем отсутствующих кодов. Коды списка, отсутствующие в СПР, не создают новинки; одинаковое название под другим кодом не заменяет нужный код. Числовой код `101` совпадает с текстовым `101`, но текстовый `00101` остаётся отдельным кодом. Пары дедуплицируются, регистр и лишние пробелы ресторанов нормализуются при сопоставлении.

Если блюдо СПР продаётся в ресторане вне списка, его продажи там не входят в новое/сезонное меню. В базе соответствующей группы они сохраняются как обычные продажи. Список задаёт рестораны запусков, а действующие каналы по-прежнему определяются по положительным продажам после запуска. Старые сохранённые данные без списка можно просматривать с пояснением о прежнем расчёте; для применения нового правила загрузите Excel с этим листом.

## Поток продаж

| Столбец | Содержание |
|---|---|
| `Позиция меню (блюдо)` | Название блюда |
| `Ресторан` | Название ресторана |
| `Подразделение` | Канал/подразделение продаж |
| `Дата_Отчет` | Дата продаж |
| `Группа меню` | Группа всех блюд для модели с весами |
| `Позиций` | Количество в штуках |

Для рейтинга с весами нужны продажи **всех блюд групп**, в которых введено оцениваемое меню, за период с запуска. Выгрузка только новинок пригодна для обычных СКП и прежнего сравнения по СКП, но не даёт полноценную базу весов. Если столбца группы нет, включается прежняя модель.

Допускаются необязательные `Позиция с коррект`, `Код` и поддержанные псевдонимы заголовков. Однозначно перепутанные заголовки `Группа меню` и `Позиций` распознаются по содержимому. Противоречие группы новинки со СПР приводит к сообщению об ошибке.

## Поток чеков

| Столбец | Содержание |
|---|---|
| `Ресторан` | Ресторан |
| `Подразделение` | Канал/подразделение |
| `Дата` | Дата |
| `Заказы` | Число заказов |

Поддерживаются многострочные заголовки с «Кол-во» и подписью «Заказов». Число позиций не должно подменять число заказов. Если «Поток чеков» отсутствует, используется подготовленный лист `ПотокЧеков`. При наличии обоих источником является «Поток чеков».

Дата может быть числовой датой Excel, `YYYY-MM-DD` или `DD.MM.YYYY`. Количество — число; допускаются текстовые числа с десятичной запятой. Значения формул должны быть сохранены в Excel: приложение читает их вычисленный результат и не пересчитывает формулы Excel.

На все сочетания ресторан/канал/дата с продажами оцениваемого меню должны быть данные заказов. Пропуски выводятся с пояснением. Текущая версия при неполной базе скрывает затронутые СКП; продажи в штуках и модель с весами используют продажи блюд и групп.

## Необязательная история до запуска

Третий режим «С учётом СКП до запуска» читает два дополнительных источника. Допустимы названия `Поток продаж_до` / `Поток продаж до` и `Поток чеков_до` / `Поток чеков до`, без учёта регистра и с пробелами вокруг. Произвольные листы со словом «до» не читаются. Два листа, претендующие на одну роль, вызывают сообщение о неоднозначности.

В продажах до нужны `Позиция меню (блюдо)`, `Ресторан`, `Подразделение`, `Дата` (также поддержан `Дата_Отчет`), `Группа меню`, `Позиций`. Обычные блюда, отсутствующие в СПР, сохраняются. Необязательные коды и скорректированные названия/псевдонимы новинок применяются так же, как в основном источнике; противоречия СПР диагностируются. Продажи новинки до её запуска исключаются и учитываются в аудите только в ресторанах из списка запусков. В остальных ресторанах эти продажи остаются в истории обычного меню.

В чеках до нужны `Ресторан`, `Подразделение`, `Дата` и число заказов. Поддерживается многострочная подпись `Кол-во / заказов, / шт.`. Поле обнаруживается отдельно в каждом листе; номера и буквы столбцов не фиксируются. Например, оно может находиться в D в истории и в F в основном источнике. Количество позиций, гостей и выручка не подменяют заказы.

Даты обоих источников читаются по фактическим значениям; поддержаны системы Excel 1900/1904. База — 14 дней непосредственно перед запуском. Основные листы также могут предоставлять эту историю перед более поздним запуском. Дополнительные источники не расширяют основной ассортимент, продажи и фильтры.

Совпадающие агрегаты пересекающихся источников берутся один раз; конфликтующие исключают затронутую базу третьего режима. Продажи и заказы должны глобально покрывать все 14 дней базы. Нерегулярный канал не обязан иметь 14 ненулевых дней. Полное отсутствие группы за базовый период означает отсутствие источника; оно не превращается в ноль. Продажи без соответствующих заказов, разные периоды выгрузок, нулевой СКП до и отрицательные количества объясняются в детализации. Два прежних режима продолжают работать без листов до; для позднего запуска третий режим может использовать подходящую историю основных листов.

Остальные листы сводных таблиц не нужны приложению. ПК, ПК_Кухня и «Кухня_по КП» не участвуют в расчётах.

Синтетический пример формата можно получить командой `npm run example`. Он не содержит рабочих данных.
